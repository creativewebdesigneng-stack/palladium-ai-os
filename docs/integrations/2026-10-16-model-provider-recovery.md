# Agent model selection and failure recovery

Issue #982 concerns a real QA agent that could not run even a minimal no-tool prompt. The authenticated owner's database record selected `model_provider=openai` and display label `model=Gemini`; three task records retained that pair and remained `running` without completion/error evidence. The wizard saved a label without a provider. Personal model credential metadata contained no connection for this owner. This confirms configuration and lifecycle defects; it does not independently reproduce the earlier production PostgREST error. Recent retained runtime logs yielded no matching error; older requested logs were outside retention.

## Repairs through the existing architecture

The wizard now persists canonical provider/model pairs. Agent writes accept existing Gemini and DeepSeek integrations; the existing visual builder offers both. A narrow compatibility mapping handles the exact old wizard labels, including the observed Gemini/OpenAI mismatch, before provider availability and entitlement checks. Other known canonical cross-vendor mismatches are rejected before queueing. Gemini's wizard choice uses the documented `gemini-2.5-flash` API ID ([Google model reference](https://ai.google.dev/gemini-api/docs/models/gemini-2.5-flash)); no existing secret is replaced and no new gateway or inference adapter is added.

Enabled personal OpenAI/Anthropic credentials retain precedence and owner/provider filters. If that optional store is unavailable, only an already-configured deployment credential for that same provider may be used. No other user's credential or vendor is substituted. A present but undecryptable personal connection fails with a safe actionable message; its failure never silently incurs deployment spending. Gemini uses the existing deployment credential path. Agent runtime calls restrict gateway fallback to their explicit provider consent; planner calls remain on their selected provider. Other callers retain their existing gateway policy. Configuration presence is not claimed as a successful provider health check.

Required audit must persist before a run is queued, and model results require audit and a confirmed owner-bound completion write. Failure persistence uses the authenticated owner client where available, validates its write receipt, and reports persistence problems instead of claiming closure. Credential resolution now lies inside cleanup/error handling in streaming, direct and planner loops. Runtime failure logs contain task ID and safe classification rather than raw exceptions. The streaming endpoint preserves safe status/code errors instead of collapsing preparation failures to generic HTTP 400 responses.

## Verification and remaining blockers

Regression tests cover the observed legacy pair, canonical wizard pairs, mismatched models, unknown providers, same-provider optional-store recovery, personal key isolation and decryption failure, Gemini's deployment path, audit denial, streamed lookup failure, absent failure/completion receipts and fallback consent. No test makes a real model request. Build, TypeScript and full application checks, then exact-commit CI and deployment evidence, are recorded in the release pull request.

The current browser is signed out. The previously identified deployed Supabase server-credential/audit problem remains unresolved through supported management access; no key, JWT or SQL authentication workaround is used. No real `QA AGENT ONLINE` response, authenticated new agent creation or persisted live inference is certified. Existing running rows are preserved for investigation, not rewritten to invented terminal outcomes. No autonomous worker, notification encryption setup or provider billing issue is claimed repaired by this batch. Phases 2–8 remain subject to their own evidence; no overall percentage is invented.
