# Trusted media verification recovery — 16 October 2026

Restores the existing trusted-video ledger and private bucket with production migration `20261016103419_restore_trusted_media_verification.sql`. The original owner-write-all draft is not replayed: authenticated clients can read their own ledger but cannot insert, update, delete or truncate verification records. Authenticated upload/finalization handlers now use the existing privileged server client, with explicit owner and asset checks. Listing remains on the caller's RLS client. Invalid privileged credentials fail without falling back to caller writes.

Storage inserts require an owned uploading ledger record and its exact object path. Client replacement and deletion are denied throughout verification and after readiness. Four restrictive policies enforce read/upload scope and replacement/deletion denial even if another permissive storage policy is broader. Other buckets retain their existing policy behavior. Trusted server access is retained; the existing handlers use signed-upload/read paths, with uploads remaining `upsert:false`. A user-facing verified-asset deletion workflow is not introduced here. No media, object, signed URL or provider publication was created in production during verification.

The shared UI/server/bucket ceiling is 50 MB, matching the current Free-plan maximum in the [Supabase storage limits documentation](https://supabase.com/docs/guides/storage/uploads/file-limits). The project-wide global limit still applies if configured lower. The previous 512 MB claim exceeded that plan's ceiling. MIME remains MP4-only. Ready ledger rows require bounded size/duration, verification time and the exact owner/asset/filename path.

The old verifier scanned arbitrary bytes for a loose `mvhd` signature. Verification now follows bounded ISO BMFF box structure, supported file brands, a movie header, a video track handler and a media-data box. It supports version-0/version-1 movie headers and movie metadata in either the first or tail range at declared box boundaries. It rejects audio-only/unsupported/truncated/duplicate metadata and signatures hidden in media payload. Streaming reads cancel above the requested range. At most the first and tail 4 MB ranges are read, with existing per-request timeouts. Unusual layouts without complete accessible movie metadata are rejected rather than guessed. These are container-metadata checks, not full codec decoding or malware scanning; reference structure: [W3C ISO BMFF note](https://www.w3.org/TR/mse-byte-stream-format-isobmff/).
